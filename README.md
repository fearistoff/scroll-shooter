# Zombie Crowd Shooter — прототип

Играбельный прототип мобильной crowd-shooter игры на three.js: отряд стрелков едет
по дороге, автоматически стреляет вперёд, собирает бонусы из бочек и проходит
ворота-множители. Волна заканчивается боссом, после него начинается следующая —
плотнее и многочисленнее. Забег кончается смертью главного стрелка; накопленный
опыт тратится между забегами на постоянные улучшения.

Вся графика — примитивы (капсулы для людей и зомби, боксы для бочек, ворот и мин,
плоскости для дороги). Модели предполагается подставить позже, поэтому геометрия
нигде не влияет на логику.

**Стек:** three.js 0.185 + TypeScript + Vite. Портретная ориентация, ввод через
pointer-события (мышь и тач).

## Запуск

```bash
npm install
```

```bash
npm run dev
```

Прочие команды: `npm run build` (проверка типов + сборка в `dist/`),
`npm run typecheck`, `npm run preview` (раздача собранного билда).

Собранная версия — PWA: устанавливается на домашний экран и **играется офлайн**.
Публикуется на GitHub Pages автоматически при push в `main`. Подробности и
ограничения — в разделе «PWA и офлайн».

## Версия

Номер версии живёт в `package.json` (поле `version`), на сборке подставляется в
код через `define` (`__APP_VERSION__`) и показывается **внизу экрана прокачки** —
там его видно перед каждым забегом, и по нему понятно, обновилось ли устройство.

Схема semver, считаем от влияния на игрока:

| Разряд      | Когда поднимается                                                     |
| ----------- | --------------------------------------------------------------------- |
| **мажорный** | геймплей заметно меняется или расширяется: новая ключевая механика, режим, переработка боя |
| **минорный** | новая фича: враг, оружие, бонус, ветка прокачки, экран                 |
| **патч**     | исправления и баланс: числа в `config.ts`, багфиксы, правки интерфейса  |

Поднимать версию — часть правки, а не отдельный шаг: меняешь поведение — меняй и
число в `package.json` в том же коммите.

## Договорённости

Их полезно знать до чтения кода — на них опирается всё остальное.

**Единицы.** 1 unit = 1 метр. Все размеры, скорости и дальности в конфиге — в
метрах и метрах в секунду.

**Оси.** Отряд стоит в `z = 0`, дорога уходит от игрока в `−Z`, всё движение мира
идёт к `+Z`. `x` — поперёк дороги (асфальт от −5 до +5), `y` — вверх. Зомби, бочки,
ворота и мины появляются в `z = −46` (за верхней кромкой кадра) и уезжают за
`z = +12`.

**Камера** статична: `fov 65`, позиция `(0, 20, 5)`, смотрит в `(0, 0, −9)` — наклон
примерно 55° вниз. Отряд оказывается на ~20% высоты кадра снизу, кадр захватывает
`z` от +4.1 до −43.3. Камера откалибрована проекцией, а не на глаз: от неё зависит
дальность оружия, высота подписей и линия остановки зомби, поэтому менять её числа
без пересчёта этих величин нельзя.

**Холст** не растягивается на окно: соотношение сторон зажато в диапазон реальных
телефонов (0.46…0.62), результат вписывается в окно и центрируется, по бокам
остаются тёмные поля. Размер отслеживается `ResizeObserver` (событие `resize`
приходит не на всякое изменение вьюпорта).

**Все числа — в `src/config.ts`.** Файл намеренно большой и с комментариями: у
каждого значения написано, откуда оно взялось, чем зажато сверху и снизу и что
сломается, если его крутить в одиночку. Значения, которые были замерены, помечены
словом «ЗАМЕРЕНО» вместе с методом замера.

**Пулинг везде.** Ни один игровой объект не создаётся и не уничтожается по ходу
забега. Массовые сущности (пули, зомби, кристаллы) — один `InstancedMesh` плюс
данные в `Float32Array`; гашение через swap-remove, поэтому активные всегда лежат
непрерывно в `[0, count)`, а `mesh.count` равен числу живых. Малочисленные сущности
(бочки, ворота, мины) — пул отдельных `Mesh`, потому что каждой нужен свой цвет.

**Текст и полоски — DOM-оверлей**, а не игровая графика: остаются резкими на любом
`devicePixelRatio` и ничего не стоят по кадру. Мировые координаты проецируются на
экран после рендера (иначе матрицы камеры не обновлены и проекция даёт мусор).

## Игровой цикл

Логика всегда получает постоянный `dt = 1/60`, рендер идёт с частотой монитора.
Накопитель ограничен сверху (`maxFrameTime`, `maxStepsPerFrame`), поэтому возврат
из фоновой вкладки не отматывает полминуты за один кадр.

Порядок одного шага в `Game.update` не произвольный:

1. `run.advance` — часы забега. Идут первыми: по ним считаются разгон плотности и
   разблокировки.
2. `updateBossPhase` — смена волны, выход босса, включение/выключение бонусов.
3. `squad.update` — ввод, движение, регенерация, выстрелы. Герой стреляет уже из
   новой позиции, пуля не отстаёт от него на кадр.
4. `enemies`, `barrels`, `gates`, `boss` — цели придвигаются и задевают отряд.
5. `mines` — после зомби: подход проверяется по их актуальным координатам.
6. `bullets` — полёт и раздача попаданий. Цели уже подвинулись, поэтому попадания
   считаются по их сегодняшним координатам, а не по прошлому кадру.
7. `crystals` — после пуль: кристалл с только что убитого зомби едет сразу.
8. `world`, `hud`, проверка конца забега.

Фаза приложения — `running | result | upgrade`. На экранах игровой шаг не идёт, но
рендер продолжается: сцена видна за оверлеем, и переход не выглядит зависанием.
Побочно это значит, что игровые таймеры (полоски HP, кулдауны) на экранах не тают.

## Механики

### Управление

Абсолютное следование: отряд стоит там, где палец. По краям холста есть мёртвая
зона (`input.deadZonePercent`, 15%) — палец в ней означает крайнее положение, а
живая полоса между зонами растягивается на весь ход отряда. И положение пальца, и
положение отряда выражены в процентах, поэтому от разрешения ничего не зависит.
Резкость гасится лерпом (`followLerp`).

Способ ввода зависит от устройства: с мышью отряд идёт за курсором простым
наведением, на тач-экране — только по касанию (палец не умеет «наводиться»).
Различаются по `event.pointerType`, так что на ноутбуке с тачскрином работают оба.

### Мир

Дорога, разметка и камни на обочине не двигаются как объекты — их координата
считается от накопленного смещения по модулю длины сегмента, поэтому дорога
бесконечна при постоянном числе мешей. Всё остальное (зомби, бочки, ворота, мины,
кристаллы) едет к `+Z` со `world.worldSpeed`; зомби добавляют к этому свою скорость.

### Отряд и строй

Герой (`heroHp` 100) и союзники (`allyHp` 30) — один список. Предел отряда
качается: без покупок это 3 стрелка считая героя, ветка прокачки «Размер отряда»
поднимает его до 23 (см. «Конец забега и прокачка»). Обрезка стоит в единственной
точке входа бойцов (`Squad.addShooters`), через неё идут и бочки, и оба типа ворот.

Строй задан шаблоном `formation.rowSizes`: герой в первом ряду один, дальше ряды
по 4, 5, 6 и 7 союзников. Видимых бойцов 22, то есть полностью купленный предел
отряда совпадает с визуальным потолком и на дороге виден весь отряд. Механика «невидимых» бойцов
(стреляют из последнего видимого места, `bulletsPerHiddenShooter`) сохранена, но
при текущем пределе не срабатывает — она нужна, если предел поднимут выше 23.

Шахматка получается из чередования чётных и нечётных рядов: ряд центрируется по
своей номинальной ширине, поэтому чётный даёт полуцелые смещения (±0.5, ±1.5 шага),
а нечётный — целые (0, ±1, ±2). Соседние ряды сдвинуты на полшага, капсулы смотрят
в промежутки. Места в ряду занимаются от середины наружу, чтобы неполный ряд
оставался центрированным и не съезжал с решётки.

Каждый стрелок несёт своё оружие и свой накопитель выстрелов со случайной фазой —
иначе одинаковые накопители давали бы залпы вместо потока.

Урон стрелкам сведён в две воронки, `hurtHero` и `hurtAlly`: только там HP
уменьшается и только там ставятся таймеры вспышки и паузы регенерации. До этого
присвоение было раскидано по шести местам, и требование «показать реакцию после
изменения значения» нельзя было выполнить надёжно.

Множитель получаемого урона применяется в этих же воронках, а не в источниках урона.
Пока множитель был один на весь отряд, источники умножали сами; теперь у героя и у
союзника свои ветки прокачки, и решать, чей множитель взять, может только та точка,
которая знает, кому достался удар. Все четыре метода урона (`damageNearestShooter`,
`damageShootersInCircle`, `damageShootersInBand`, `damageAllShooters`) передают в
воронку СЫРОЙ урон.

У целей воронки свои — `EnemyPool.applyDamage`, `Boss.applyDamage`,
`BarrelField.applyDamage`, — и в них же применяется **сопротивление урону**
(`damageResistance`, множитель ко входящему урону): у зомби 1, у босса 0.5, у бочек
0.75. Поскольку множитель живёт в воронке, его одинаково учитывают и попадания пуль,
и взрывы мин, а места попадания о нём не знают. Поле должно быть у каждой цели, даже
когда равно 1: воронка читает его безусловно, и без поля выходит `damage * undefined`
= `NaN`, после чего проверка `hp > 0` ложна и цель умирает от первого попадания.

Автоматическая регенерация — `player.regen`, сейчас 1 hp за 2 секунды, начисляется
непрерывно, а не пульсом: при пульсе исход боя зависел бы от того, попал удар за
миллисекунду до тика или после, а такую случайность игрок не может ни увидеть, ни
отыграть. Лечение включается только через `delayAfterDamageSeconds` = 10 после
последнего попадания, и таймер у каждого стрелка свой: зомби бьют чаще, чем раз в
10 секунд, поэтому в стычке регенерации нет вовсе, а весь отыгрыш достаётся паузам
между ними.

Оба числа базовые: и скорость, и задержку каждая половина отряда домножает на свой
множитель прокачки (`regenRateMultiplier`, `regenDelayMultiplier`), поэтому герой и
союзники лечатся по-разному. Обе ветки по 15 уровней: скорость по 0.1 hp/сек за
уровень (0.5 → 2.0), задержка по 0.5 секунды (10 → 2.5). Предел задержки специально
оставлен БОЛЬШЕ интервала удара зомби (около секунды): опустись он ниже — таймер
истекал бы между ударами, и регенерация превратилась бы в постоянное вычитание из
входящего урона, ровно то, против чего задержка и введена.

### Оружие и пули

Четыре ступени стрелкового оружия (пистолет → пистолет-пулемёт → автомат → пулемёт)
при единой дальности 16.1 дают лестницу примерно по ×1.5 урона в секунду на
ступень: 2.2 × 1 = 2.2, 5 × 0.67 = 3.35, 7 × 0.71 = 4.97, 15 × 0.5 = 7.5. Растёт
именно урон, а темп огня задан отдельно и служит характером ствола — пистолет
пощёлкивает, пулемёт поливает. По обычному зомби (1 hp) лестница доходит не
целиком: урон меньше единицы тратит остаток впустую, попаданий нужно 1, 2, 2 и 2,
и убийств в секунду выходит 2.2, 2.5, 3.5 и 7.5. Полностью расчётный DPS доходит
по толстым целям — крупному зомби, боссу, бочкам. Бочка с оружием поднимает ствол
всего отряда на следующую ступень. Особое оружие (огнемёт — 25 × 0.36 = 9,
гранатомёт — 0.67 × 15 = 10) достаётся ОДНОМУ бойцу и заменяет его ствол целиком;
сначала герою, потом случайному союзнику.

**Гранатомёт бьёт по площади.** Его 15 урона за выстрел разделены на 10 прямым
попаданием и 5 взрывом в круге радиуса 2 вокруг точки попадания — тем же кругом и
через те же воронки урона, что и взрыв мины, поэтому он одинаково достаёт зомби,
босса и бочки, а сопротивление урону у каждого учитывается само. Прямая цель стоит
в центре круга и получает обе части, то есть против одиночной толстой цели ствол
остался ровно тем же, что и был. Разница вся по толпе: 5 урона с запасом убивают
обычного зомби (1 hp) и не убивают крупного (30 hp). Замер одинокого героя за 60
секунд — 58 убитых против 37 у того же ствола без взрыва при 68 у пулемёта: взрыв
подтянул особое оружие к вершине стрелковой лестницы, не поставив его над ней.
Ворота под взрыв не подпадают — стену граната ломает только прямым попаданием. Признак «особое» выводится из того, что
ствола нет в списке прогрессии, — отдельного флага на бойце нет.

**Всё оружие, кроме пистолета, сначала покупается в магазине** (см. «Деньги и
магазин оружия»). Пока ствол не куплен, бочка с ним не появляется на забеге
вовсе — ни в цепочке стрелкового, ни среди особого. Замок по покупке накладывается
ПОВЕРХ замка по времени (`run.unlocks.weapons`): ствол должен быть и куплен между
забегами, и дожить до своей секунды внутри забега. Оба сходятся в одной функции,
`BarrelField.isWeaponAllowed`.

Дальность задана в units, а не в процентах экрана, чтобы не зависеть от
соотношения сторон телефона. Пуля гаснет, пройдя `range`; линия гашения ложится на
70.2% высоты кадра. Отсюда механика из ТЗ: до дальних бочек пули не долетают, надо
подпускать.

Попадание считается не точкой, а отрезком, который пуля прошла за шаг
(`collision.ts`): при скорости 24 units/сек за кадр она проходит 0.4 units и могла
бы перескочить цель. Отрезок проверяется против круга (зомби, босс, бочка) или
против плиты (секция ворот).

### Зомби

Два вида: обычный (1 hp, урон 5) и крупный (30 hp, урон 25). Хитбокс для попаданий
шире модели в 1.5 раза. Зомби идут к отряду, останавливаются на линии `stopZ` с
разбросом (без разброса толпа выстраивается идеальной стеной) и бьют ближайшего
стрелка в пределах `attackReachX`. Первый удар — не сразу по прибытии, а через
`firstAttackDelay`: у игрока есть окно на реакцию, и «дошёл» не означает «попал».

**Смерть — падение набок.** Убитый зомби за 0.1 секунды (`deathAnim.fallSeconds`)
заваливается вправо или влево (сторона разыгрывается в момент смерти) и остаётся
лежать на дороге. Ось поворота — у ПОДОШВЫ, а не в центре капсулы: точка опоры
остаётся там, где зомби стоял, а тело едет по дуге вокруг неё и ложится рядом,
в половине своей длины вбок. Замерено: подошва не сдвигается ни на кадре падения,
нижняя точка тела ровно на дороге при любом наклоне. Тело больше не идёт само, но мир продолжает наезжать на камеру и
уносит его вниз: исчезает оно только за нижним краем экрана. По телам не попасть
пулей, они не взводят мины и не показывают полосок HP.

Живые и тела делят ОДИН пул на 800 слотов (`enemies.poolSize`), поэтому тело занимает
место, пока не уедет. Замер на шести минутах: при полном отряде с пулемётом на дороге
одновременно бывает до 179 живых и 29 тел — до предела вчетверо.

Плотность потока считается в одном месте, `EnemyPool.spawnInterval`, и складывается
из трёх множителей:

- **разгон по времени забега** (`spawn.ramp`): интервал сжимается от 1.6 до 0.28 с
  за первую минуту. Ведёт разгон время, а не доля израсходованного бюджета —
  давление растёт независимо от того, успевает игрок или нет;
- **размер отряда** (`spawn.squadScale`): интервал делится на
  `1 + 0.03 × (стрелков − 1)`. Сложность идёт за силой игрока;
- **номер волны** (`run.waveSpawnRateGrowth`): каждая следующая волна плотнее
  предыдущей в 1.5 раза.

### Темп, волны и разблокировки

Волна — это бюджет зомби (`run.waveZombieCount` = 300 единиц в первой волне) плюс
босс в конце. Счётчик на полосе считает каждого за единицу и показывает, сколько
осталось до босса. Бюджет наполняется заново с каждой волной и растёт тем же темпом,
что и плотность (`waveBudgetGrowth` = `waveSpawnRateGrowth`), поэтому длительность
волны держится примерно постоянной, а густеет только толпа.

**Крупные зомби входят в бюджет со второй волны** (`run.bigZombieFromWave`), и их
доля РАСТЁТ линейно, по `run.bigZombieShareStep` за волну: 10% во второй, 20% в
третьей, 30% в четвёртой и так далее до потолка `bigZombieShareMax` (сейчас 100%, то
есть с одиннадцатой волны обычных зомби в бюджете не остаётся). Доля считается от
ОБЩЕГО числа единиц волны, поэтому она меняет только состав толпы, но не количество и
не длительность волны: единиц всегда `waveZombieCount × waveBudgetGrowth^(волна − 1)`,
и первая волна не оказывается короче прочих из-за отсутствия крупных. Внутри волны
состав бюджета уже не меняется, а вид каждого зомби тянется из остатков
пропорционально — крупные равномерно рассеяны по всей волне.

Гейт стоит на НОМЕРЕ ВОЛНЫ, хотя раньше стоял на секунде забега, и это разные вещи.
Секунда наступала посреди волны, а до неё бюджет крупных просто ждал, поэтому волна
распадалась надвое: сначала ~270 обычных подряд, потом — когда обычные кончались и
замок уступал, чтобы дорога не пустовала, — толпа из 30 крупных. Номер волны такого
разрыва создать не может: запирать внутри волны нечего, и досрочного выпуска больше
не требуется.

ЗАМЕРЕНО (бюджет волны выбирается до конца через `RunState.takeNextZombie`): в первой
волне 300 единиц и **ни одного** крупного; во второй 45 крупных на 450 единиц (ровно
10%), первый на 6-м спавне, подряд не больше 2, промежуток между крупными не больше 36
обычных, по пятым долям волны 7/8/9/11/10; в третьей 135 на 675 (20%), первый на 10-м,
подряд не больше 5, промежуток не больше 22, по пятым долям 25/32/27/24/27. По бюджету
волн (обычные/крупные): 300/0, 405/45, 540/135, 709/304, 911/608, 1139/1139 — и с
одиннадцатой волны 0/17300, то есть только крупные.

Прочее содержимое закрыто до определённой секунды забега (`run.unlocks`): каждая
ступень оружия, бочки со стрелками и минами, оба типа ворот. Это не расписание —
появление остаётся случайным, разблокировка лишь снимает запрет. Часы идут сквозь
волны и не обнуляются, иначе игрок навсегда остался бы с пистолетными ограничениями.

Первый зомби волны выходит сразу, не выжидая интервал: с ожиданием (1.6 с у
одиночки) пустая дорога тянулась 5.5 секунды.

### Бочки

**На экране одновременно бывает только один бонус** — бочка или ворота; стена из двух
секций и колонна турникетов считаются одним бонусом. Пока бонус на дороге, следующий
не выезжает, а подошедший тик спавна ждёт: как только экран освободился, бонус выходит
почти сразу. Замерено на 600 с игрового времени: 6.3 бонуса в минуту против 16.6 без
правила, дорога при этом занята 96% времени — находок стало в 2.6 раза меньше, но
пустой дороги не появилось.

Бочка едет сверху, над ней написана прочность; попадания её уменьшают, на 50% и 25%
меняется цвет и появляются трещины, при нуле бочка ломается и отдаёт содержимое:
ступень оружия, доп. стрелков (1–3), особое оружие или мины. Прочность зависит от
содержимого — чем ценнее находка, тем дороже вскрыть; у бочки со стрелками
прочность считается за каждого бойца (8–20 hp на бойца, то есть до 60 hp за трёх).

Бочка со стрелками — намеренно редкая находка: её вес выпадения 0.11 против 1 у
остальных типов, и на отрезке 30–300 с она попадается примерно в 5 раз реже, чем при
равных весах (10.8% спавнов против 49.2%). Вместе с поднятой прочностью это значит,
что рост отряда нужно и дождаться, и заработать.

Бесполезные бочки не появляются вовсе: с оружием — если отряд уже на последней
ступени или следующая ещё закрыта, со стрелками — если отряд упёрся в предел.
Проверка на спавне, а не на вскрытии: иначе игрок расстреливал бы такую бочку
впустую, а патроны и время в crowd-shooter и есть ресурс.

От целой бочки можно увернуться — тогда ни бонуса, ни урона. Наезд бьёт всех
стрелков в вертикальной полосе шириной хитбокса на всю глубину строя (катящаяся
бочка проходит колонну целиком), уроном крупного зомби. Своего числа у этого урона
нет: он читается из `enemies.big.damagePerHit`, потому что две константы, обязанные
совпадать, разошлись бы при первой правке.

### Ворота

**Сейчас ворота отключены целиком** (`gates.spawn.chance` = 0): и двойная стена типа
A, и колонна турникетов типа B. Пока идёт эксперимент, отряд растёт только от бочек.
Код, размеры и разблокировки на месте — включаются одним числом в конфиге. Описание
ниже — про включённое состояние.

**Тип A** — стена из двух секций, красной и синей, со значениями от −4 до +4.
Стена не пускает пули: попадание растит значение секции на 1, но не чаще раза в
`shootHitCooldown` (1 секунда) — иначе темп роста равнялся бы скорострельности
отряда (23 стрелка с пулемётом дают 345 попаданий в секунду), и механика
«дострелить стену» сводилась бы к одному касанию. Теперь она зависит от того,
сколько секунд стена в прицеле. Кулдаун считается на каждую секцию отдельно.

**Тип B** — колонна турникетов «+1» одна за другой; простреливаются насквозь и от
стрельбы не меняются. Одноразовые: сработавший исчезает сразу, а не проезжает
дальше сквозь строй. Прибавку применяет любой прошедший стрелок, не только герой.

Ворота сдвинуты от центра дороги — с одной стороны всегда остаётся проезд мимо.

### Мины

Бочка с миной расставляет их разом примерно на середине поля перед отрядом. Через
1–2 секунды каждая взводится (меняет цвет), а как только к любой взведённой мине
подходит зомби — детонируют все сразу, каждая своим кругом на 20 hp. Урон
фиксированный, поэтому крупный зомби взрыв переживёт. Взрыв задевает и бочки, и
босса: цели площадного урона регистрируются в `MineField` через интерфейс.

### Кристаллы и опыт

С убитых зомби и разбитых бочек падают кристаллы. Кристалл едет вместе с миром и
одновременно стягивается по x к отряду — поток сходится к игроку и читается как
«собирается», а не «проезжает мимо». Сбор автоматический на линии отряда.

Опыт начисляется в единственном месте, `RunState.addExp`, и копится СЫРЫМ — ровно
столько, сколько подобрано кристаллов. Именно это число стоит в счётчике HUD.

Множитель прокачки применяется один раз, на выходе из забега (`RunState.expEarned`,
зовётся из `Game.finishRun`). Раньше он умножал каждое начисление, и счётчик рос
дробными шагами непонятного размера. Разница не в арифметике — она та же, — а в том,
что видит игрок: во время забега честная единица за кристалл, а прибавка от прокачки
читается разом на экране результата. Там же рядом написано, из чего она получилась
(«Опыт за забег · 64 × 2.00»): без подписи выросшее число выглядит ошибкой счётчика.

Опыт всё равно может быть дробным (кристалл ×1.5). На экран выводится округлённое
значение, а цены сравниваются с точным: округление на каждом кристалле незаметно
съедало бы прогресс.

### Деньги и магазин оружия

Вторая валюта. Падает **только с убитых зомби** и только с вероятностью 30%
(`money.dropChance`) — с бочек, ворот и мин денег нет. Размер находки зависит от
того, кого убили: обычный зомби 1–5, крупный 3–9, босс 50–200. Награда с босса
растёт вместе с его запасом прочности — тем же множителем `run.hpMultiplier`, то
есть ×1.2 за волну: иначе время на босса росло бы, а доход нет.

Выпадение целиком в одной воронке, `MoneyPool.dropFrom`: и зомби, и босс зовут её,
поэтому бросок вероятности и диапазоны лежат в одном месте. Босс своего шанса не
имеет намеренно — он тот же зомби, просто крупный.

Монета — низкий жёлтый цилиндр, поставленный на ребро лицом к камере и вращающийся
вокруг вертикали. Летит и собирается ровно как кристалл EXP: общий `PickupPool`
держит движение к отряду, стягивание по x и сбор на его линии, а `CrystalPool` и
`MoneyPool` задают поверх него только вид и числа.

За деньги в магазине (вкладка «Оружие» на экране прокачки) НАВСЕГДА открывается
оружие: пистолет-пулемёт 1000, автомат 2500, пулемёт 5000, огнемёт 7500,
гранатомёт 10 000. Покупка строго последовательная, поэтому открытый набор всегда
префикс списка — в сохранении лежит его длина, а не перечень ключей, и
непоследовательное состояние просто нечем выразить.

Покупка не выдаёт ствол в руки, а разрешает ему **выпадать из бочек**. В самом
забеге всё как было: оружие берётся из бочки и теряется со смертью героя. Пока не
куплено ничего, у отряда только пистолет, и бочек с оружием на забеге не бывает —
остаются бочки со стрелками и с миной.

ЗАМЕРЕНО (авто-игрок, чистый прогресс, 8 забегов до смерти героя): 67 ± 2.4 секунды
на забег, 81 убитый, **71 ± 10 денег за забег**, то есть 0.87 денег с убийства при
расчётных 0.9 (30% × среднее 3). До пистолета-пулемёта — около 15 таких забегов,
на всю цепочку в 26 000 их ушло бы порядка 370. Оценка это ПОТОЛОК времени, а не
ожидание: авто-игрок гоняется за зомби, не подбирает бочки со стрелками и потому
ни разу не доходит до босса — самой крупной статьи дохода (50–200 за штуку против
1–5 с обычного зомби).

### Босс

Выходит, когда волна зачищена: бюджет исчерпан и на поле не осталось зомби. Пока
он на поле, бочки и ворота не спавнятся, а огонь отряда автоматически наводится на
него. Доезжает до ~38% высоты кадра и чередует две атаки:

- **AoE** — красный круг-телеграф на земле, через 1.2 секунды бьёт 25 hp по всем,
  кто в круге. Круг намечается по позиции отряда в момент телеграфа, поэтому уводом
  отряда урон можно избежать. Это единственный «скилловый» момент забега;
- **по всем** — неуклоняемые 6.25 hp сразу всем стрелкам.

Урон обеих атак уменьшен вдвое (было 50 и 12.5): босс встречается каждую волну, а его
удары растут вместе с ней (`run.waveDamageGrowth`), поэтому на поздних волнах прежние
числа снимали героя за один-два удара. Соотношение 4:1 между уклоняемым и
неуклоняемым уроном сохранено.

Босс — тоже зомби, поэтому замах у него тот же, что у толпы: за 1.2 секунды до удара
капсула плавно раздувается до 1.2 своего размера (от подошвы, а не от центра), а
после удара сжимается обратно за 0.1 секунды. Амплитуда и время сжатия читаются из
`enemies.attackAnim` — своих копий в секции босса нет. Время замаха равно
`telegraphTime`, поэтому у AoE раздувание начинается ровно тогда, когда на землю
ложится круг, и оба сигнала читаются как один. Для неуклоняемого удара по всем
телеграфа не было вообще — теперь замах предупреждает и о нём. На выходе (пока босс
едет к точке остановки) он не раздувается: атак ещё нет.

HP многослойное: полоса из 16 слоёв, урон снимает верхний. Слои — представление
одного числа, а не отдельные пулы HP, поэтому «×N осталось» и суммарное HP всегда
согласованы.

Смерть босса не заканчивает забег, а открывает следующую волну. Падает он так же,
как толпа: капсула валится набок за те же 0.1 секунды и уезжает с дорогой за нижний
край экрана. Тело живёт отдельным мешем — волна успевает смениться в том же кадре, в
котором босс умер, и общий меш пришлось бы гасить сразу.

### Конец забега и прокачка

Забег кончается только смертью главного стрелка. Победы как исхода не существует —
счётом стал номер достигнутой волны, он и выводится в заголовок экрана результата.

**Экран результата открывается не сразу.** Сначала идёт сцена прощания: ходьба
останавливается целиком (мир, зомби, пули и часы забега замирают), герой падает
набок за 0.1 секунды, и ещё 0.3 секунды кадр стоит — только потом появляется экран.
Это фаза `dying` в `Game.update`, и шагает в ней ровно одна вещь, падение героя.
Побочный эффект намеренный: после смерти герой уже не может получить добивающий удар,
а время на экране результата — ровно то, что было в момент гибели.

Опыт уходит в банк в любом случае: копить за проигрыш нормально для rogue-like,
иначе неудачный забег не даёт вообще ничего. Между забегами он тратится на улучшения
по 50 уровней. Шаг маленький (1–4% за уровень), цена растёт на 18.5% за уровень, так
что 50-й уровень стоит на два порядка дороже первого. Собранные деньги уходят в свой
банк тем же образом, но без множителя: сколько подобрано, столько и зачислено.

**Валюты две, и тратятся они на разное.** EXP качает числа игрока уровнями,
деньги разово открывают оружие (см. «Деньги и магазин оружия»). Источники тоже
разные — опыт падает со всего подряд, деньги только с зомби и только иногда, —
поэтому две ветви прогрессии не конкурируют за один ресурс. `MetaProgress` держит
оба банка и обе покупки, `applyTo()` по-прежнему пишет в конфиг только множители:
открытое оружие в конфиг не попадает, его спрашивают у магазина напрямую.

Две ветки регенерации живут по своим числам: 15 уровней вместо 50 и собственный
знаменатель цены (`costGrowth` в самом улучшении перекрывает общий), растягивающий
её ровно от 500 до 8000 EXP за уровень. Дорого относительно боевых веток — там
первый уровень стоит 8–25 EXP; числа заданы пользователем.

**Главный герой и доп. стрелки качаются отдельно.** Шесть боевых характеристик —
урон, скорострельность, дальность, получаемый урон, скорость восстановления HP и
задержка перед началом лечения — существуют в двух экземплярах,
своя ветка у героя и своя у стрелков; опыт и размер отряда остались общими — ни то,
ни другое не характеристика стрелка. На экране прокачки это таббар из четырёх
вкладок: «Герой», «Стрелки», «Оружие» (магазин) и «Прочее». Точка на вкладке
означает, что там есть что купить прямо сейчас, — иначе доступная покупка в
закрытой вкладке ничем себя не выдаёт. Порядок вкладок задан в `screens.ts`
(`TRACK_ORDER`), а не порядком `UPGRADE_TRACKS`: магазин не ветка улучшений и в
том списке его нет.

Подписи боевых характеристик у обеих веток общие (`COMBAT_LABELS` в `meta.ts`
раздаётся обеим ветвям ссылкой на один объект): набор характеристик один и тот же,
кого качаем — сказано вкладкой, поэтому формулировки безличные («скорость лечения»,
а не «скорость лечения героя»).

Цены и шаги у обеих боевых веток одинаковые. Разделение само по себе уже удвоило
стоимость прежнего эффекта (раньше одна покупка усиливала весь отряд), а что ценнее,
зависит от момента забега: каждый забег начинается одним героем, а к концу волны
доходит до 22 союзников. Выбор «сильное начало или сильный конец» и есть смысл
разделения; при разных ценах он превратился бы в арифметику «что выгоднее за EXP».

Множитель урона союзника ложится ПОВЕРХ `formation.allyDamageFactor`: тот задаёт
базовую долю от героя (0.3), ветка стрелков усиливает саму долю.

**Размер отряда — тоже улучшение, и единственное, которое считается в штуках.**
Уровень даёт не процент, а бойца: 3 стрелка без покупок, 20 уровней по одному,
23 на последнем — ровно визуальный потолок строя. Такие улучшения перечислены в
`COUNT_UPGRADES` (`meta.ts`), значение считается как `base + step × level`, и в
строке экрана вместо множителя стоит «3 → 4». Цены заданы по краям: 200 EXP за
4-го стрелка и 5000 за 23-го, знаменатель 1.184611 = 25^(1/19) выведен из них,
вся ветка стоит 31 001 EXP. Ветка заодно поднимает сложность: бочка со стрелками
перестаёт спавниться при полном отряде, а поток зомби ускоряется от числа стволов
(`enemies.spawn.squadScale`), так что купленные бойцы приводят с собой толпу плотнее.

Сохранения, сделанные до разделения, читаются: старый ключ раскладывается по обеим
новым веткам сразу (`MetaProgress.migrateLegacy`). Иначе разделение стало бы скрытым
нерфом — союзники внезапно откатились бы к нулю. Версия ключа `localStorage` поэтому
и не менялась. Полей `money` и `weapons` в сохранениях до появления магазина нет —
такой игрок сохраняет уровни улучшений и начинает магазин с нуля.

`reset()` («Сбросить прогресс») стирает и деньги, и открытое оружие: иначе «сброс»
оставлял бы половину прогрессии на месте.

Улучшения не влияют на генерацию мира — только на числа, относящиеся к игроку.
Множители пишутся в конфиг АБСОЛЮТНЫМИ значениями, поэтому `applyTo` идемпотентен
и не нужен снимок исходного состояния. Прогресс лежит в `localStorage`; чтение
обёрнуто в try/catch с проверкой и зажимом каждого поля — испорченные данные не
должны валить игру.

### Интерфейс

Слева вверху — опыт и рядом с ним деньги, по центру полоса волны с числом
оставшихся и черепом, под ней номер волны, справа секундомер. HP главного стрелка и
отладочная строка счётчиков — внизу. Полоса волны на боссфайте превращается в его
многослойную полосу HP.

Красные полоски HP над зомби показываются 3 секунды после получения урона:
постоянные полоски над сотней целей превратили бы экран в кашу, а таймаут оставляет
только тех, кто участвует в бою прямо сейчас. У стрелков правило другое — полоска
висит, пока запас не полный. Их единицы, а регенерация сама гасит полоску, когда HP
отыграется, поэтому недолеченный боец виден всё время, а не первые три секунды.
Числа HP над зомби убраны совсем — следствие в том, что у крупного зомби до первого
попадания индикатора нет.

На узком холсте (`viewport.narrowWidthPx`) полоса волны опускается под верхнюю
строку: EXP, полоса и секундомер в неё одновременно не влезают. Признак ставит
`Viewport` классом на контейнер, а не медиа-запрос — тот смотрит на окно, а холст
letterbox'ится и бывает заметно меньше.

## PWA и офлайн

Собранная игра — устанавливаемое приложение, работающее без сети целиком.
Внешних запросов у неё нет вообще: three.js попадает в бандл, шрифт системный,
иконки локальные, эмодзи берутся из системы. Поэтому предкеша сборки достаточно,
чтобы играть офлайн.

**Как собрано.** Плагин `precacheServiceWorker` в `vite.config.ts` на хуке
`writeBundle` собирает список всех файлов вывода и генерирует `dist/sw.js` с этим
списком внутри. Список нельзя зашить руками: имена ассетов содержат хеш
содержимого и меняются с каждой сборкой. Имя кеша — хеш содержимого всей сборки,
поэтому новая сборка всегда получает новый кеш, а старый удаляется при активации
воркера.

Хешируется именно содержимое, а не список имён: `index.html`, манифест и иконки
зовутся всегда одинаково, и правка одной только разметки оставила бы версию
прежней — `sw.js` вышел бы байт-в-байт тем же, браузер не увидел бы обновления.
Проверено: добавление комментария в `index.html` при неизменном бандле меняет
версию кеша (`e52fc471dd72` → `181ae779a207`), а имя бандла остаётся прежним.

Воркбокс намеренно не используется: предкешировать нужно единицы файлов, логика
укладывается в несколько десятков строк, а зависимость пришлось бы обновлять.

**Регистрация** — в `main.ts`, только в PROD: в dev-режиме воркер перехватывал бы
запросы Vite и ломал HMR. Путь относительный (`./sw.js`), потому что `base` сборки
`'./'` — игра может стоять в подпапке. Флаг `updateViaCache: 'none'` не даёт брать
сам скрипт воркера из HTTP-кеша, иначе новая сборка могла бы не подхватиться.

### Стратегия: документ из сети, остальное из кеша

`index.html` — единственный файл сборки с постоянным именем, и именно он называет
имя бандла (`assets/index-<хеш>.js`). Поэтому документ берётся **network-first**, с
`cache: 'reload'` (мимо HTTP-кеша браузера) и пределом ожидания в 3 секунды, а кеш
для него — запасной вариант. Свежий документ тянет за собой свежий скрипт, так что
обновление приезжает целиком и за одну перезагрузку.

Обход HTTP-кеша тут не перестраховка: GitHub Pages отдаёт `index.html` с
`Cache-Control: max-age=600` и заголовки на нём не настраиваются — без `reload`
новая версия до десяти минут не видна даже при живой сети.

Остальное — cache-first по предкешу. Промах по своему origin догружается из сети и
**кладётся в кеш**: свежий `index.html` просит бандл, которого в кеше текущей
версии ещё нет, и без этого между приходом нового документа и установкой нового
воркера игра осталась бы без офлайн-запуска.

**Обновление.** Новый воркер вызывает `skipWaiting` и `clients.claim`, поэтому
свежая сборка применяется со следующей загрузки страницы, без ручной очистки.
ЗАМЕРЕНО на `vite preview`: страница под старым воркером после одной перезагрузки
получает новые заголовок, бандл и имя кеша, старый кеш при этом удаляется.

Чего это НЕ чинит: самый первый заход, когда воркера ещё нет. Там документ живёт
по правилам раздачи (на Pages — те же 10 минут), и повлиять на это из кода нельзя.
Со второго захода всё идёт через воркер.

**Обновление при выключенной сети** не происходит вовсе — это и есть офлайн-режим:
отдаётся последняя закешированная сборка. ЗАМЕРЕНО с погашенной раздачей: документ
поднимается из кеша за 11 мс, ждать 3 секунды не приходится — отказ соединения
приходит сразу, предел ожидания нужен для мёртвой сети при живом Wi-Fi, где `fetch`
не отклоняется, а висит.

**Проверка офлайна.** Собрать, поднять раздачу, открыть, затем ПОГАСИТЬ сервер и
перезагрузить страницу:

```bash
npm run build && npm run preview
```

Игра должна подняться и играться при мёртвом сервере. Проверялось именно так, и
именно так нашлась неочевидная ошибка: раздача присылает `Vary: Origin`, а
модульный скрипт браузер грузит в режиме CORS, добавляя заголовок `Origin`. В
предкеш ответ попал по запросу воркера, у которого `Origin` нет, — по `Vary` это
другой запрос, `cache.match` промахивался, и офлайн документ поднимался, а бандл
получал 504, то есть игра стартовала пустым экраном. Поэтому в воркере стоит
`ignoreVary: true` — для предкеша статики `Vary` только мешает.

### Ограничение: нужен защищённый контекст

Service worker'ы работают только на `localhost` и по `https`. Открытая по
`http://192.168.1.45:5173` игра с телефона запустится, но **воркер не
зарегистрируется и офлайна не будет** — в консоли останется предупреждение из
`main.ts`. Это ограничение браузеров, а не игры.

Варианты для проверки на устройстве:

- выложить `dist/` на любой статический хостинг с https;
- поднять туннель к локальному серверу (`cloudflared tunnel`, `ngrok`) — он даёт
  https-адрес;
- на самом телефоне открыть `http://localhost`, если раздача идёт с него же.

На iOS приложение нужно добавить на домашний экран («Поделиться» → «На экран
"Домой"»): полноэкранный режим и иконку там задают мета-теги
`apple-mobile-web-app-*` в `index.html`, манифест Safari для этого не читает.

## Отладка

В dev-сборке в консоли доступны `__game` и `__config`:

```js
__config.world.worldSpeed = 12;           // числа крутятся на живой игре
__game.squad.debugSnapshot();             // строй, HP, оружие каждого бойца
__game.enemies.debugSnapshot();           // все ЖИВЫЕ зомби на поле
__game.enemies.debugCorpses();            // тела: где лежат и на сколько завалились
__game.run.debugSnapshot();               // волна, бюджет, множители, часы
```

`debugSnapshot` есть почти у каждой подсистемы — через них удобно проверять
поведение детерминированно, шагая `__game.update(1/60)` при остановленном цикле
(`__game.stop()`).

## Что стоит знать

Особенности, которые видны только в замерах, но сильно влияют на ощущения:

**Узкое место отряда — прицеливание, а не урон.** Зомби расходятся по ширине
дороги до ±4.25, а пули летят узкой колонной шириной строя (±2.16). Поэтому
изменения, добавляющие плотность или снижающие HP зомби, не обмениваются один к
одному: водить отряд по дороге обязательно, само не выкосится.

**Босс не масштабируется по волнам.** Его 1000 hp фиксированы, а полный отряд из 23
стрелков с пулемётом даёт 345 урона в секунду, из которых сопротивление 0.5 пропускает
172.5 — то есть босс живёт около 6 секунд, и с ростом волны он перестаёт быть
препятствием. Два множителя тянут в разные стороны: урезание отряда с 50 до 23 и
сопротивление урону вместе удлинили боссфайт вчетверо против прежних ~1.3 секунды —
препятствием он всё равно не стал.

**Урон от зомби достаётся союзникам, а не герою.** Герой — цель только когда он
единственный стрелок; пока в отряде есть хоть один союзник, бьют ближайшего из них.
Ограничения по расстоянию у удара нет, поэтому дошедший зомби всегда кого-то
задевает, и персональные 30 hp союзника — основной расходуемый ресурс отряда.
