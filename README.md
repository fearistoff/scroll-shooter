# Zombie Crowd Shooter — прототип

Играбельный прототип мобильной crowd-shooter игры на three.js: отряд стрелков едет
по дороге, автоматически стреляет вперёд, собирает бонусы из бочек и проходит
ворота-множители. Волна заканчивается боссом, после него начинается следующая —
плотнее и многочисленнее. Забег кончается смертью главного стрелка; накопленный
опыт тратится между забегами на постоянные улучшения.

Вся графика — примитивы (капсулы для людей и зомби, боксы для бочек, ворот и мин,
плоскости для дороги). Модели предполагается подставить позже, поэтому геометрия
нигде не влияет на логику.

**Стек:** three.js 0.185 + TypeScript + Vite. Портретная ориентация, ввод через
pointer-события (мышь и тач).

## Запуск

```bash
npm install
```

```bash
npm run dev
```

Прочие команды: `npm run build` (проверка типов + сборка в `dist/`),
`npm run typecheck`, `npm run preview` (раздача собранного билда).

Собранная версия — PWA: устанавливается на домашний экран и **играется офлайн**.
Публикуется на GitHub Pages автоматически при push в `main`. Подробности и
ограничения — в разделе «PWA и офлайн».

## Договорённости

Их полезно знать до чтения кода — на них опирается всё остальное.

**Единицы.** 1 unit = 1 метр. Все размеры, скорости и дальности в конфиге — в
метрах и метрах в секунду.

**Оси.** Отряд стоит в `z = 0`, дорога уходит от игрока в `−Z`, всё движение мира
идёт к `+Z`. `x` — поперёк дороги (асфальт от −5 до +5), `y` — вверх. Зомби, бочки,
ворота и мины появляются в `z = −46` (за верхней кромкой кадра) и уезжают за
`z = +12`.

**Камера** статична: `fov 65`, позиция `(0, 20, 5)`, смотрит в `(0, 0, −9)` — наклон
примерно 55° вниз. Отряд оказывается на ~20% высоты кадра снизу, кадр захватывает
`z` от +4.1 до −43.3. Камера откалибрована проекцией, а не на глаз: от неё зависит
дальность оружия, высота подписей и линия остановки зомби, поэтому менять её числа
без пересчёта этих величин нельзя.

**Холст** не растягивается на окно: соотношение сторон зажато в диапазон реальных
телефонов (0.46…0.62), результат вписывается в окно и центрируется, по бокам
остаются тёмные поля. Размер отслеживается `ResizeObserver` (событие `resize`
приходит не на всякое изменение вьюпорта).

**Все числа — в `src/config.ts`.** Файл намеренно большой и с комментариями: у
каждого значения написано, откуда оно взялось, чем зажато сверху и снизу и что
сломается, если его крутить в одиночку. Значения, которые были замерены, помечены
словом «ЗАМЕРЕНО» вместе с методом замера.

**Пулинг везде.** Ни один игровой объект не создаётся и не уничтожается по ходу
забега. Массовые сущности (пули, зомби, кристаллы) — один `InstancedMesh` плюс
данные в `Float32Array`; гашение через swap-remove, поэтому активные всегда лежат
непрерывно в `[0, count)`, а `mesh.count` равен числу живых. Малочисленные сущности
(бочки, ворота, мины) — пул отдельных `Mesh`, потому что каждой нужен свой цвет.

**Текст и полоски — DOM-оверлей**, а не игровая графика: остаются резкими на любом
`devicePixelRatio` и ничего не стоят по кадру. Мировые координаты проецируются на
экран после рендера (иначе матрицы камеры не обновлены и проекция даёт мусор).

Зависимости идут в одну сторону: `entities` и `ui` знают про `config` и `core`, но

реализует, но сам о них ничего не знает.

## Игровой цикл

Логика всегда получает постоянный `dt = 1/60`, рендер идёт с частотой монитора.
Накопитель ограничен сверху (`maxFrameTime`, `maxStepsPerFrame`), поэтому возврат
из фоновой вкладки не отматывает полминуты за один кадр.

Порядок одного шага в `Game.update` не произвольный:

1. `run.advance` — часы забега. Идут первыми: по ним считаются разгон плотности и
   разблокировки.
2. `updateBossPhase` — смена волны, выход босса, включение/выключение бонусов.
3. `squad.update` — ввод, движение, регенерация, выстрелы. Герой стреляет уже из
   новой позиции, пуля не отстаёт от него на кадр.
4. `enemies`, `barrels`, `gates`, `boss` — цели придвигаются и задевают отряд.
5. `mines` — после зомби: подход проверяется по их актуальным координатам.
6. `bullets` — полёт и раздача попаданий. Цели уже подвинулись, поэтому попадания
   считаются по их сегодняшним координатам, а не по прошлому кадру.
7. `crystals` — после пуль: кристалл с только что убитого зомби едет сразу.
8. `world`, `hud`, проверка конца забега.

Фаза приложения — `running | result | upgrade`. На экранах игровой шаг не идёт, но
рендер продолжается: сцена видна за оверлеем, и переход не выглядит зависанием.
Побочно это значит, что игровые таймеры (полоски HP, кулдауны) на экранах не тают.

## Механики

### Управление

Абсолютное следование: отряд стоит там, где палец. По краям холста есть мёртвая
зона (`input.deadZonePercent`, 15%) — палец в ней означает крайнее положение, а
живая полоса между зонами растягивается на весь ход отряда. И положение пальца, и
положение отряда выражены в процентах, поэтому от разрешения ничего не зависит.
Резкость гасится лерпом (`followLerp`).

Способ ввода зависит от устройства: с мышью отряд идёт за курсором простым
наведением, на тач-экране — только по касанию (палец не умеет «наводиться»).
Различаются по `event.pointerType`, так что на ноутбуке с тачскрином работают оба.

### Мир

Дорога, разметка и камни на обочине не двигаются как объекты — их координата
считается от накопленного смещения по модулю длины сегмента, поэтому дорога
бесконечна при постоянном числе мешей. Всё остальное (зомби, бочки, ворота, мины,
кристаллы) едет к `+Z` со `world.worldSpeed`; зомби добавляют к этому свою скорость.

### Отряд и строй

Герой (`heroHp` 100) и союзники (`allyHp` 30) — один список. Предел отряда 23
стрелка, считая героя; обрезка стоит в единственной точке входа бойцов
(`Squad.addShooters`), через неё идут и бочки, и оба типа ворот.

Строй задан шаблоном `formation.rowSizes`: герой в первом ряду один, дальше ряды
по 4, 5, 6 и 7 союзников. Видимых бойцов 22, то есть предел отряда совпадает с
визуальным потолком и на дороге виден весь отряд. Механика «невидимых» бойцов
(стреляют из последнего видимого места, `bulletsPerHiddenShooter`) сохранена, но
при текущем пределе не срабатывает — она нужна, если предел поднимут выше 23.

Шахматка получается из чередования чётных и нечётных рядов: ряд центрируется по
своей номинальной ширине, поэтому чётный даёт полуцелые смещения (±0.5, ±1.5 шага),
а нечётный — целые (0, ±1, ±2). Соседние ряды сдвинуты на полшага, капсулы смотрят
в промежутки. Места в ряду занимаются от середины наружу, чтобы неполный ряд
оставался центрированным и не съезжал с решётки.

Каждый стрелок несёт своё оружие и свой накопитель выстрелов со случайной фазой —
иначе одинаковые накопители давали бы залпы вместо потока.

Урон стрелкам сведён в две воронки, `hurtHero` и `hurtAlly`: только там HP
уменьшается и только там ставится таймер полоски. До этого присвоение было
раскидано по шести местам, и требование «полоска после изменения значения» нельзя
было выполнить надёжно.

Автоматическая регенерация — `player.regen`, сейчас 1 hp за 3 секунды, начисляется
непрерывно, а не пульсом: при пульсе исход боя зависел бы от того, попал удар за
миллисекунду до тика или после, а такую случайность игрок не может ни увидеть, ни
отыграть.

### Оружие и пули

Четыре ступени стрелкового оружия (пистолет → мини-автомат → автомат → пулемёт)
отличаются только темпом огня: 2, 5, 7 и 15 выстрелов в секунду при уроне 1 и
единой дальности 16.1. Бочка с оружием поднимает ствол всего отряда на следующую
ступень. Особое оружие (огнемёт, гранатомёт) достаётся ОДНОМУ бойцу и заменяет его
ствол целиком; сначала герою, потом случайному союзнику. Признак «особое» выводится
из того, что ствола нет в списке прогрессии, — отдельного флага на бойце нет.

Дальность задана в units, а не в процентах экрана, чтобы не зависеть от
соотношения сторон телефона. Пуля гаснет, пройдя `range`; линия гашения ложится на
70.2% высоты кадра. Отсюда механика из ТЗ: до дальних бочек пули не долетают, надо
подпускать.

Попадание считается не точкой, а отрезком, который пуля прошла за шаг
(`collision.ts`): при скорости 24 units/сек за кадр она проходит 0.4 units и могла
бы перескочить цель. Отрезок проверяется против круга (зомби, босс, бочка) или
против плиты (секция ворот).

### Зомби

Два вида: обычный (1 hp, урон 5) и крупный (30 hp, урон 25). Хитбокс для попаданий
шире модели в 1.5 раза. Зомби идут к отряду, останавливаются на линии `stopZ` с
разбросом (без разброса толпа выстраивается идеальной стеной) и бьют ближайшего
стрелка в пределах `attackReachX`. Первый удар — не сразу по прибытии, а через
`firstAttackDelay`: у игрока есть окно на реакцию, и «дошёл» не означает «попал».

Плотность потока считается в одном месте, `EnemyPool.spawnInterval`, и складывается
из трёх множителей:

- **разгон по времени забега** (`spawn.ramp`): интервал сжимается от 1.6 до 0.175 с
  за первую минуту. Ведёт разгон время, а не доля израсходованного бюджета —
  давление растёт независимо от того, успевает игрок или нет;
- **размер отряда** (`spawn.squadScale`): интервал делится на
  `1 + 0.03 × (стрелков − 1)`. Сложность идёт за силой игрока;
- **номер волны** (`run.waveSpawnRateGrowth`): каждая следующая волна плотнее
  предыдущей в 1.5 раза.

### Темп, волны и разблокировки

Волна — это бюджет зомби (`run.normalZombieCount` + `bigZombieCount`, в первой
волне 264 + 36) плюс босс в конце. Счётчик на полосе считает каждого за единицу и
показывает, сколько осталось до босса. Бюджет наполняется заново с каждой волной и
растёт тем же темпом, что и плотность (`waveBudgetGrowth` = `waveSpawnRateGrowth`),
поэтому длительность волны держится примерно постоянной, а густеет только толпа.

Часть содержимого закрыта до определённой секунды забега (`run.unlocks`): крупные
зомби, каждая ступень оружия, бочки со стрелками и минами, оба типа ворот. Это не
расписание — появление остаётся случайным, разблокировка лишь снимает запрет. Часы
идут сквозь волны и не обнуляются, иначе игрок навсегда остался бы с пистолетными
ограничениями.

У разблокировок есть исключение, без которого игра замирала: **если обычные зомби
кончились, а крупные ещё закрыты, крупные выходят досрочно.** Иначе сильный отряд
выбивал весь бюджет обычных к 62-й секунде и до 120-й на дороге не было никого при
счётчике «осталось 37». Правило «не простаивать» важнее правила «крупные не раньше
двух минут». По той же причине первый зомби волны выходит сразу, не выжидая
интервал.

### Бочки

Бочка едет сверху, над ней написана прочность; попадания её уменьшают, на 50% и 25%
меняется цвет и появляются трещины, при нуле бочка ломается и отдаёт содержимое:
ступень оружия, доп. стрелков (1–3), особое оружие или мины. Прочность зависит от
содержимого — чем ценнее находка, тем дороже вскрыть; у бочки со стрелками
прочность считается за каждого бойца.

Бесполезные бочки не появляются вовсе: с оружием — если отряд уже на последней
ступени или следующая ещё закрыта, со стрелками — если отряд упёрся в предел.
Проверка на спавне, а не на вскрытии: иначе игрок расстреливал бы такую бочку
впустую, а патроны и время в crowd-shooter и есть ресурс.

От целой бочки можно увернуться — тогда ни бонуса, ни урона. Наезд бьёт всех
стрелков в вертикальной полосе шириной хитбокса на всю глубину строя (катящаяся
бочка проходит колонну целиком), уроном крупного зомби. Своего числа у этого урона
нет: он читается из `enemies.big.damagePerHit`, потому что две константы, обязанные
совпадать, разошлись бы при первой правке.

### Ворота

**Тип A** — стена из двух секций, красной и синей, со значениями от −4 до +4.
Стена не пускает пули: попадание растит значение секции на 1, но не чаще раза в
`shootHitCooldown` (1 секунда) — иначе темп роста равнялся бы скорострельности
отряда (23 стрелка с пулемётом дают 345 попаданий в секунду), и механика
«дострелить стену» сводилась бы к одному касанию. Теперь она зависит от того,
сколько секунд стена в прицеле. Кулдаун считается на каждую секцию отдельно.

**Тип B** — колонна турникетов «+1» одна за другой; простреливаются насквозь и от
стрельбы не меняются. Одноразовые: сработавший исчезает сразу, а не проезжает
дальше сквозь строй. Прибавку применяет любой прошедший стрелок, не только герой.

Ворота сдвинуты от центра дороги — с одной стороны всегда остаётся проезд мимо.

### Мины

Бочка с миной расставляет их разом примерно на середине поля перед отрядом. Через
1–2 секунды каждая взводится (меняет цвет), а как только к любой взведённой мине
подходит зомби — детонируют все сразу, каждая своим кругом на 20 hp. Урон
фиксированный, поэтому крупный зомби взрыв переживёт. Взрыв задевает и бочки, и
босса: цели площадного урона регистрируются в `MineField` через интерфейс.

### Кристаллы и опыт

С убитых зомби и разбитых бочек падают кристаллы. Кристалл едет вместе с миром и
одновременно стягивается по x к отряду — поток сходится к игроку и читается как
«собирается», а не «проезжает мимо». Сбор автоматический на линии отряда.

Опыт дробный (множитель прокачки даёт нецелые кристаллы) и начисляется в
единственном месте, `RunState.addExp`, — поэтому множитель применяется там же, а
счётчик в HUD и сумма на экране результата согласованы по определению. На экран
выводится округлённое значение, а цены сравниваются с точным: округление на каждом
кристалле незаметно съедало бы прогресс.

### Босс

Выходит, когда волна зачищена: бюджет исчерпан и на поле не осталось зомби. Пока
он на поле, бочки и ворота не спавнятся, а огонь отряда автоматически наводится на
него. Доезжает до ~38% высоты кадра и чередует две атаки:

- **AoE** — красный круг-телеграф на земле, через 1.2 секунды бьёт 50 hp по всем,
  кто в круге. Круг намечается по позиции отряда в момент телеграфа, поэтому уводом
  отряда урон можно избежать. Это единственный «скилловый» момент забега;
- **по всем** — неуклоняемые 12.5 hp сразу всем стрелкам.

HP многослойное: полоса из 16 слоёв, урон снимает верхний. Слои — представление
одного числа, а не отдельные пулы HP, поэтому «×N осталось» и суммарное HP всегда
согласованы.

Смерть босса не заканчивает забег, а открывает следующую волну.

### Конец забега и прокачка

Забег кончается только смертью главного стрелка. Победы как исхода не существует —
счётом стал номер достигнутой волны, он и выводится в заголовок экрана результата.

Опыт уходит в банк в любом случае: копить за проигрыш нормально для rogue-like,
иначе неудачный забег не даёт вообще ничего. Между забегами он тратится на пять
улучшений по 50 уровней: урон, скорострельность, дальность, получаемый урон и сам
опыт. Шаг маленький (1–2% за уровень), цена растёт на 11.5% за уровень, так что
50-й уровень стоит на два порядка дороже первого.

Улучшения не влияют на генерацию мира — только на числа, относящиеся к игроку.
Множители пишутся в конфиг АБСОЛЮТНЫМИ значениями, поэтому `applyTo` идемпотентен
и не нужен снимок исходного состояния. Прогресс лежит в `localStorage`; чтение
обёрнуто в try/catch с проверкой и зажимом каждого поля — испорченные данные не
должны валить игру.

### Интерфейс

Слева вверху — опыт, по центру полоса волны с числом оставшихся и черепом, под ней
номер волны, справа секундомер. HP главного стрелка и отладочная строка счётчиков —
внизу. Полоса волны на боссфайте превращается в его многослойную полосу HP.

Красные полоски HP над стрелками и зомби показываются 3 секунды после получения
урона. Постоянные полоски над десятками цели превратили бы экран в кашу, а таймаут
показывает только тех, кто участвует в бою прямо сейчас. Числа HP над зомби убраны
совсем — следствие в том, что у крупного зомби до первого попадания индикатора нет.

На узком холсте (`viewport.narrowWidthPx`) полоса волны опускается под верхнюю
строку: EXP, полоса и секундомер в неё одновременно не влезают. Признак ставит
`Viewport` классом на контейнер, а не медиа-запрос — тот смотрит на окно, а холст
letterbox'ится и бывает заметно меньше.

## PWA и офлайн

Собранная игра — устанавливаемое приложение, работающее без сети целиком.
Внешних запросов у неё нет вообще: three.js попадает в бандл, шрифт системный,
иконки локальные, эмодзи берутся из системы. Поэтому полного предкеша сборки
достаточно, никаких стратегий на runtime-запросы не нужно.

**Как собрано.** Плагин `precacheServiceWorker` в `vite.config.ts` на хуке
`writeBundle` собирает список всех файлов вывода и генерирует `dist/sw.js` с этим
списком внутри. Список нельзя зашить руками: имена ассетов содержат хеш
содержимого и меняются с каждой сборкой. Имя кеша — хеш от списка и от содержимого
нехешированных файлов (манифест, иконки), поэтому новая сборка всегда получает
новый кеш, а старый удаляется при активации воркера.

Воркбокс намеренно не используется: предкешировать нужно единицы файлов, логика
укладывается в несколько десятков строк, а зависимость пришлось бы обновлять.

**Регистрация** — в `main.ts`, только в PROD: в dev-режиме воркер перехватывал бы
запросы Vite и ломал HMR. Путь относительный (`./sw.js`), потому что `base` сборки
`'./'` — игра может стоять в подпапке. Флаг `updateViaCache: 'none'` не даёт брать
сам скрипт воркера из HTTP-кеша, иначе новая сборка могла бы не подхватиться.

**Обновление.** Новый воркер вызывает `skipWaiting` и `clients.claim`, поэтому
свежая сборка применяется со следующей загрузки страницы, без ручной очистки.

**Проверка офлайна.** Собрать, поднять раздачу, открыть, затем ПОГАСИТЬ сервер и
перезагрузить страницу:

```bash
npm run build && npm run preview
```

Игра должна подняться и играться при мёртвом сервере. Проверялось именно так, и
именно так нашлась неочевидная ошибка: раздача присылает `Vary: Origin`, а
модульный скрипт браузер грузит в режиме CORS, добавляя заголовок `Origin`. В
предкеш ответ попал по запросу воркера, у которого `Origin` нет, — по `Vary` это
другой запрос, `cache.match` промахивался, и офлайн документ поднимался, а бандл
получал 504, то есть игра стартовала пустым экраном. Поэтому в воркере стоит
`ignoreVary: true` — для предкеша статики `Vary` только мешает.

### Ограничение: нужен защищённый контекст

Service worker'ы работают только на `localhost` и по `https`. Открытая по
`http://192.168.1.45:5173` игра с телефона запустится, но **воркер не
зарегистрируется и офлайна не будет** — в консоли останется предупреждение из
`main.ts`. Это ограничение браузеров, а не игры.

Варианты для проверки на устройстве:

- выложить `dist/` на любой статический хостинг с https;
- поднять туннель к локальному серверу (`cloudflared tunnel`, `ngrok`) — он даёт
  https-адрес;
- на самом телефоне открыть `http://localhost`, если раздача идёт с него же.

На iOS приложение нужно добавить на домашний экран («Поделиться» → «На экран
"Домой"»): полноэкранный режим и иконку там задают мета-теги
`apple-mobile-web-app-*` в `index.html`, манифест Safari для этого не читает.

## Отладка

В dev-сборке в консоли доступны `__game` и `__config`:

```js
__config.world.worldSpeed = 12;           // числа крутятся на живой игре
__game.squad.debugSnapshot();             // строй, HP, оружие каждого бойца
__game.enemies.debugSnapshot();           // все зомби на поле
__game.run.debugSnapshot();               // волна, бюджет, множители, часы
```

`debugSnapshot` есть почти у каждой подсистемы — через них удобно проверять
поведение детерминированно, шагая `__game.update(1/60)` при остановленном цикле
(`__game.stop()`).

## Замеренные ориентиры

Числа, полученные замером, а не оценкой. Полезны, чтобы понимать масштаб при правках.

| Величина | Значение |
| --- | --- |
| Отряд на экране | 20% высоты кадра снизу |
| Линия гашения пули | 70.2% высоты кадра |
| Кадр по глубине | `z` от +4.1 до −43.3 |
| Глубина строя | 2.4 units за героем из доступных 4.16 |
| Ширина самого широкого ряда | ±2.16 units при разбросе зомби ±4.25 |
| Зомби на дороге за первые 30 с | 25 при отряде из одного стрелка |
| Длительность волны 1 | ~126 с одиночкой, ~122 с полным отрядом |
| Длительность волн 2+ | ~53 с одиночкой, ~21 с полным отрядом |
| Наездов бочки до смерти героя | 4 (100 hp / 25) |

## Что стоит знать

Особенности, которые видны только в замерах, но сильно влияют на ощущения:

**Узкое место отряда — прицеливание, а не урон.** Зомби расходятся по ширине
дороги до ±4.25, а пули летят узкой колонной шириной строя (±2.16). Поэтому
изменения, добавляющие плотность или снижающие HP зомби, не обмениваются один к
одному: водить отряд по дороге обязательно, само не выкосится.

**Босс не масштабируется по волнам.** Его 1000 hp фиксированы, а полный отряд из 23
стрелков с пулемётом снимает их примерно за 3 секунды (345 урона в секунду), так что
с ростом волны он перестаёт быть препятствием. Прежний предел в 50 стрелков давал
вдвое больше, то есть после урезания отряда боссфайт стал вдвое длиннее — но
препятствием всё равно не стал.

**Урон от зомби достаётся союзникам, а не герою.** Герой — цель только когда он
единственный стрелок; пока в отряде есть хоть один союзник, бьют ближайшего из них.
Ограничения по расстоянию у удара нет, поэтому дошедший зомби всегда кого-то
задевает, и персональные 30 hp союзника — основной расходуемый ресурс отряда.
