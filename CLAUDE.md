# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Прототип мобильного crowd-shooter на three.js + TypeScript + Vite. Подробное описание
механик — в [README.md](README.md); здесь то, что нужно, чтобы менять код не вслепую.

## Команды

```bash
npm run dev        # vite, порт 5173, host: true (открывается с телефона по IP)
npm run build      # tsc --noEmit && vite build — ошибки типов валят сборку
npm run typecheck  # только проверка типов
npm run preview    # раздача собранного dist, порт 4173
```

**Тестового раннера в проекте нет.** Поведение проверяется детерминированным
прогоном игры через dev-хуки — это основной способ убедиться, что правка работает:

```js
__game.stop();                          // остановить цикл, чтобы шагать вручную
__game.update(1 / 60);                  // ровно один шаг логики
__game.enemies.debugSnapshot();          // debugSnapshot есть почти у каждой подсистемы
__config.enemies.normal.hp = 5;          // числа крутятся на живой игре
```

Так измеряются и балансовые правки: прогнать N забегов авто-игроком (наводить
`__game.input.targetPercent` на ближайшую цель), собрать статистику. Разброс между
забегами большой — σ около 27 секунд по времени выживания, поэтому по одному
прогону выводы делать нельзя.

Публикация — push в `main`, дальше [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)
собирает и выкладывает `dist/` на GitHub Pages. В CI стоит `npm ci`, поэтому после
любого `npm install` обновлённый `package-lock.json` нужно коммитить — иначе
публикация падает на первом шаге.

## Архитектура

### Game — единственный владелец

[`src/core/game.ts`](src/core/game.ts) держит сцену, рендер, камеру и все подсистемы.
**Порядок создания в конструкторе разрывает цикл зависимостей** и менять его нельзя
произвольно: `crystals → enemies(run, crystals) → mines(enemies) → squad(bullets, mines)
→ barrels(squad, crystals, run, bonusSlot) → gates(squad, run, bonusSlot) →
boss(squad, run, crystals)`, и только потом `mines.addAreaTarget(barrels/boss)` и
`bonusSlot.add(barrels/gates)`.

[`src/entities/bonusSlot.ts`](src/entities/bonusSlot.ts) — общий слот: **на экране
одновременно допустим один бонус**, бочка ИЛИ ворота (стена или колонна турникетов
целиком считается одним). Оба поля спрашивают разрешение у слота, а не друг у друга,
иначе бочки и ворота замкнулись бы взаимной зависимостью. Правило стоит только в
потоках спавна, поэтому явный `spawn()` из замерочных скриптов работает как раньше.

**Порядок внутри `update(dt)` тоже смысловой**, а не случайный:

1. `run.advance` — часы забега первыми: по ним считаются разгон плотности и разблокировки;
2. `updateBossPhase` — смена волны и выход босса;
3. `squad.update` — герой стреляет уже из новой позиции, пуля не отстаёт на кадр;
4. `enemies`, `barrels`, `gates`, `boss` — цели придвигаются;
5. `mines` — после зомби, подход считается по актуальным координатам;
6. `bullets` — попадания разбираются по уже подвинувшимся целям;
7. `crystals` — после пуль, чтобы кристалл с только что убитого зомби стартовал сразу.

**`dt` не постоянный.** [`src/core/loop.ts`](src/core/loop.ts) шагает по длине кадра
устройства: на 120 Гц это 1/120, на 60 Гц — 1/60, длинный кадр дробится на равные
подшаги не длиннее `CONFIG.loop.maxStepDt`. Поэтому в логике не должно быть ничего «за
кадр»: интервалы — накопителем (`таймер -= interval`, а не `= 0`), события у линии —
пересечением (`prevZ < 0 && z >= 0`), а не попаданием в узкое окно. Потолок шага стоит
ровно ради тех мест, где окно всё-таки есть (створка турникета 0.3 units при скорости
мира 6 units/с). Ручной прогон замерочными скриптами (`__game.update(1 / 60)`) от этого
не меняется, и разброс между dt проверялся: за 60 с спавн совпадает точно, убитые —
13.9 ± 4.5 при 1/60 против 13.5 ± 6.5 при 1/120 (8 прогонов).

Фазы приложения: `running | dying | result | upgrade`. Игра **открывается экраном
прокачки**. На экранах `update` возвращается сразу, поэтому игровые таймеры (полоски HP,
вспышки, кулдаун ворот) там не тают — это специально.

**Пауза — не фаза, а признак поверх неё** (`Game.paused`): с неё возвращаются туда же,
откуда ушли. Гасит она шаг ИЗ ЦИКЛА, а не сам `Game.update`, поэтому
`__game.update(1 / 60)` из замерочных скриптов шагает игру и на паузе — иначе случайная
потеря фокуса тихо останавливала бы замер. Вешается на Esc, на контейнер секундомера в
HUD и на уход приложения в фон (`blur` + `visibilitychange`); возврат фокуса паузу не
снимает — продолжает игрок сам.

### Пулинг

Ни один игровой объект не создаётся по ходу забега. Массовые сущности (пули, зомби,
кристаллы) — `InstancedMesh` плюс данные в `Float32Array`, гашение через swap-remove,
активные непрерывно в `[0, count)`, `mesh.count` равен числу живых.

**Добавляя новый массив данных, обязательно проведите его через `recycle` (перенос из
последнего слота) и обнулите в `spawn`.** Иначе новый объект унаследует таймер
предыдущего: так уже ловились ложные полоски HP и вспышки у только что появившихся зомби.

Цвет инстанса задаётся через `instanceColor`, а материал при этом БЕЛЫЙ: three умножает
одно на другое, и с цветным материалом вспышка не смогла бы стать светлее его.

### Интерфейсы объявлены на стороне потребителя

`SquadTarget` живёт в `enemies.ts`, `BonusReceiver` в `barrels.ts`, `GateTarget` в
`gates.ts`, `BossTarget` в `boss.ts`, `AreaDamageReceiver`/`EnemyProbe` в `mines.ts`.
`Squad` их реализует, но сам о них не знает — поэтому `entities` и `ui` не зависят от
`Game`. Новую связь между подсистемами вводите так же: узкий интерфейс у того, кто
вызывает.

### Воронки урона

HP уменьшается только в пяти местах, и там же ставятся таймеры полосок и вспышек:
`EnemyPool.applyDamage`, `Squad.hurtHero`, `Squad.hurtAlly`, `Boss.applyDamage`,
`BarrelField.applyDamage`. Раньше присвоение было раскидано по шести точкам, и требование
«показать полоску после изменения HP» невыполнимо было соблюсти. Новый источник урона
подключайте через них.

Там же применяется **сопротивление урону** (`damageResistance` — множитель ко входящему
урону): у зомби 1, у босса 0.5, у бочек 0.75. Поскольку оно живёт в воронке, его
одинаково учитывают и попадания пуль, и взрывы мин, а места попадания о нём не знают.

В воронках отряда так же применяется **множитель получаемого урона от прокачки** —
у героя и у союзника он свой (`player.heroMultipliers` / `player.allyMultipliers`).
Источники урона (`damageNearestShooter`, `damageShootersInCircle`,
`damageShootersInBand`) передают СЫРОЙ урон: чей множитель брать, знает только та
точка, которая уже выбрала цель.

Отдельно: зомби бьют героя **только когда он единственный стрелок** — пока есть союзники,
удар достаётся ближайшему из них. Одиночная атака босса идёт через тот же
`damageNearestShooter`, поэтому правило распространяется и на неё. Ограничения по расстоянию у удара нет (параметр
`attackReachX` убран), поэтому дошедший зомби всегда кого-то задевает: уводом отряда
поперёк дороги урон толпы больше не обнуляется.

### Забег и волны

[`src/core/run.ts`](src/core/run.ts) держит бюджет волны, часы, EXP и скорость мира. Босс волну не
заканчивает: после его смерти `startNextWave()` наполняет бюджет заново, а плотность и
количество растут одним темпом (`waveSpawnRateGrowth`, `waveBudgetGrowth`), поэтому
длительность волны держится постоянной. Часы и EXP идут сквозь волны — по часам считаются
разблокировки.

**Скорость наезда мира читается из `RunState.worldSpeed`, а не из
`CONFIG.world.worldSpeed`.** В конфиге номинальное значение (цель разгона), в забеге —
фактическое: на боссфайте оно уходит в ноль за `world.stopEaseSeconds`, и вместе с
дорогой замирает всё, что она везёт (декор, зомби и тела, бочки, ворота, мины,
выходящий босс). Переключает это одно место — `Game.updateBossPhase`. Новый объект,
который «едет с миром», подключайте туда же; единственное исключение — кристаллы и
монеты: дорога их не везёт вовсе, они с места выпадения улетают в счётчики HUD
(`pickupFlight`, путь считается в пикселях холста через `CameraSpace`).

Плотность потока считается в одном месте, `EnemyPool.spawnInterval`: разгон по времени ×
размер отряда × номер волны. Там же живёт правило «пул полон — ждём слот и бюджет не
тратим»: иначе единица волны списывалась бы, не став зомби (так терялась большая часть
поздних волн).

### Мета-прокачка

[`src/core/meta.ts`](src/core/meta.ts) пишет множители в `CONFIG.player` **абсолютными
значениями**, поэтому `applyTo()` идемпотентен и снимок исходного состояния не нужен.
Хранится в `localStorage`. Улучшения не влияют на генерацию мира — только на числа игрока.

Ветки разделены: свой набор боевых характеристик у главного героя
(`player.heroMultipliers`), свой у доп. стрелков (`player.allyMultipliers`), опыт общий.
Раскладку по вкладкам экрана задаёт `UPGRADE_TRACKS` — разметка вкладок и строк
собирается из него, в HTML её нет. Аксессоры оружия (`weaponDamage`, `weaponFireRate`,
`weaponRange`) требуют `ShooterKind` вторым аргументом; умолчания у него нет намеренно,
иначе союзники тихо получали бы числа героя.

Сохранения до разделения читаются: `migrateLegacy` кладёт старый уровень в ОБЕ новые
ветки. Ключ `localStorage` при этом не менялся — смена версии стёрла бы прогресс.

Осторожно: `meta.reset()` пишет в `localStorage` и стирает прогресс. В замерочных
скриптах вместо него подменяйте множители в памяти и возвращайте обратно.

### Интерфейс

Весь текст и полоски — DOM-оверлей поверх холста, не игровая графика: текст резкий на
любом `devicePixelRatio`. [`src/ui/labels.ts`](src/ui/labels.ts) проецирует мировые
координаты в экранные **после** `renderer.render` — до него матрицы камеры не обновлены
и проекция даёт мусор. Работает в режиме «перерисовать список за кадр»: `begin()` →
`add()`/`addBar()` → `end()`.

Отладочная строка счётчиков внизу — только в dev (`import.meta.env.DEV`), в PROD блок
скрыт и строка даже не собирается.

## Конвенции

**Все числовые параметры — в [`src/config.ts`](src/config.ts).** Файл намеренно большой:
у каждого значения написано, откуда оно взялось, чем зажато сверху и снизу и что сломается,
если крутить его в одиночку. Ставя новое число, добавляйте туда же обоснование.

**Пометка «ЗАМЕРЕНО» означает проверенное значение, а не оценку.** Если меняете число,
рядом с которым стоит замер, — либо перезамерьте, либо явно напишите, что старый замер
к новому значению не относится. Несколько раз уже случалось, что комментарий утверждал
измеренное, будучи догадкой.

**Проверяйте измерением, а не на глаз.** Проекцию через игровую камеру (куда на экране
попадает мировая координата), фактические размеры DOM-элементов, попадания бинарным
поиском по координате. Так найдены неочевидные вещи: `Vary: Origin` ломал офлайн-кеш,
дальность оружия считалась не от того, `visualViewport` на iOS занижает высоту.

**Комментарии и коммиты — по-русски**, как и весь существующий код.

**Версию поднимайте в том же коммите, что и правку.** Единственное место —
поле `version` в `package.json`; в код она попадает через `define` в
[`vite.config.ts`](vite.config.ts) (`__APP_VERSION__`, объявлен в
[`src/env.d.ts`](src/env.d.ts)) и выводится внизу экрана прокачки. Разряд по
влиянию на игрока: **мажорный** — геймплей заметно меняется или расширяется
(новая ключевая механика, режим, переработка боя); **минорный** — новая фича
(враг, оружие, бонус, ветка прокачки, экран); **патч** — исправления, баланс,
правки интерфейса. Правка без изменения поведения (комментарии, рефакторинг,
документация) версию не двигает. **Вместе с версией добавляйте запись в
[`src/ui/changelog.ts`](src/ui/changelog.ts)** — список для экрана «Что нового»,
который открывается нажатием на номер версии; пишется руками и только про то,
что игрок способен заметить.

**Единицы и оси:** 1 unit = 1 метр; отряд в `z = 0`, дорога уходит в `−Z`, всё едет к
`+Z`, `x` поперёк дороги (±5), `y` вверх. Спавн в `z = −46`, despawn за `z = +12`.
Камера откалибрована проекцией — от неё зависят дальность оружия, высота подписей и
линия остановки зомби, поэтому её числа нельзя менять без пересчёта этих величин.

**Высота страницы:** `100dvh` в браузере и `100vh` в установленном приложении
(медиа-запрос `display-mode`). На iOS в standalone `dvh` на момент запуска отдаёт
заниженное значение.

**PWA:** `dist/sw.js` генерируется плагином в [`vite.config.ts`](vite.config.ts) — список
предкеша собирается из фактического вывода сборки, править сгенерированный файл
бессмысленно. При локальной проверке собранной версии сначала снимайте старый service
worker и его кеши, иначе он отдаёт бандл прошлой сборки и маскирует изменения.

Документ воркер берёт **из сети** (network-first, `cache: 'reload'`, кеш — запасной
вариант), всё остальное — из кеша. `index.html` — единственный файл с постоянным именем,
и он называет имя бандла: отдай его из кеша — и устройство осталось бы на старой версии
до установки нового воркера, то есть всегда на перезагрузку позади. Версия кеша считается
по содержимому всей сборки, а не по списку имён, — иначе правка одной разметки не сменила
бы `sw.js` и обновления бы не случилось.

**`.gitignore` прячет корневые `*.md` и `*.png`** (исходное ТЗ и референсные скриншоты),
`README.md` возвращён исключением. Добавляя документ в корень, проверьте, не попал ли он
под шаблон.
